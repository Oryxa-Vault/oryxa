Oryxa multiplayer AI — many people, many agents, one room v0.5 · Apache 2.0 · Go

AI is single-player.Oryxa makes it multiplayer.

Your Claude Code session and your colleague's Codex session are two private terminals that will never know about each other. Oryxa puts them in the same room, on the same question, in front of the same people. Neither CLI was modified, and neither knows the other is there.

The gap

Your framework owns the agent. Nobody owns the room.

Every agent framework assumes one caller. One session, one prompt, one reply, one person holding the terminal. AI is single-player by construction. The moment a second person needs to see what the agent is doing — or add a correction while it's mid-turn, or take over the thread after lunch — you are writing that yourself.

Oryxa is that layer and nothing else. To the framework, Oryxa is one user. To your team, it's a shared room. Your prompts, tools, memory and multi-agent orchestration stay exactly where they are.

The core is open source. Apache 2.0, Go, one binary — the room, the event log, the connector engine, the shim and the viewer. Not a hosted product with a repo attached: docker compose up is the whole thing.

Who answers

A turn is an agent doing work, so silence is a feature.

A connector declares what it engages on, and the room works out who a message is for — an agent mentioned by name, one that declared an interest in what you said, or nobody at all when you're asking a colleague directly or just saying thanks.

This starts as an optimisation and stops being one the moment a turn is a whole agentic loop rather than a single model call. 133 calls versus 35 is a pleasant saving when a call is cheap, and a different product when it's a three-minute coding turn.

Connecting your agent

A connector is a description of HTTP calls, not code.

Nothing in the core knows any framework's name — that's what keeps both sides free. Drop a file in ./connectors/ or POST it at runtime, and you're done. No Go required.

Seven genuinely different surfaces, one core, one YAML file each. CrewAI is the sharpest test of the boundary: a crew is multi-agent by design, so one Oryxa turn becomes several LLM calls between the crew's own agents — and Oryxa sees one turn with one result. Their orchestration stays theirs.

Claude Code and Codex have no HTTP surface at all — they read stdin and write JSON lines. A shim puts a server in front of one, and then it is an ordinary connector reading an ordinary stream. The command line lives in the shim's own config file, never in a connector, because a spec that could name a command to run would turn connector registration into remote code execution.

Shared context

Two lines, and an agent joins the room's thinking.

A room has state alongside its transcript — notes, decisions, working values everyone can read and write. It's a fold over the same event log, so it survives a restart and every change is attributed.

A stale write is refused with what is current, so the caller can merge instead of guessing. Loud conflicts beat clever merges: a silent overwrite leaves state that is syntactically fine and semantically wrong, and surfaces much later as an agent behaving oddly.

Honest limits

What isn't built yet.

The coding agents can write, and that is the sharp edge.

Both shipped CLI agents write inside their working directory, because read-only made them worse colleagues than they needed to be — an agent that cannot run the tests cannot verify anything. Anyone who can reach that room can cause writes to that directory. They are confined differently: Codex by the OS sandbox, Claude Code by path-patterned permissions only. Point it at a checkout you can throw away.

Rooms are scoped — each carries a secret, and turns are budgeted per room and per server. A room key binds a name to a capability, so a name can be proved rather than claimed, and every message records which. All of it is off by default so the two-minute quickstart stays two minutes; none of it should be off anywhere else.

Still missing: agents have no owners, so the room's idea of who is in it is "everyone who has spoken"; no presence; turns are bounded per minute but not in flight at once; and events carry neither a hash chain nor token counts, so the log is durable but not tamper-evident and cost per turn cannot be derived from it. PLAN.md in the repo is the source of truth and carries the same list with the reasoning for each.

/v1 is stable. The connector spec is stable and additive — new fields, never changed meanings — so a connector written today keeps working.
