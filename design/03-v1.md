# Oryxa v1 — Shared Sessions + Context + Ledger

**Date:** 2026-08-05
**Status:** draft for review
**Scope cut from:** [design/02-domains.md](02-domains.md) (which stays the target architecture)

v1 is a shared, durable, multiplayer context space that any agent joins by pointing at one URL
— with every event attributed, chained, and accountable.

Three domains: **Sessions**, **Context**, **Ledger**. No tasks, no routing, no orchestration —
whatever framework the agent already runs keeps orchestrating. That's the substrate line from
§3.5 of the domain doc, held from day one rather than promised for later.

---

## 1. The Temporal shape

Temporal's integration story is one connection string; everything else is the server's problem.

```
┌──────────────┐        join, read, write, subscribe       ┌──────────────────┐
│  Your agent  │ ◄──────────────────────────────────────►  │   Oryxa server   │
│  (unchanged) │                                            │   sessions       │
└──────────────┘                                            │   context        │
┌──────────────┐                                            │   event log      │
│  Your other  │ ◄──────────────────────────────────────►   │   ledger         │
│  agent       │                                            └──────────────────┘
└──────────────┘                    SSE                              ▲
┌──────────────┐ ◄───────────────────────────────────────────────────┘
│    Humans    │
└──────────────┘
```

**Clients connect out; nothing connects in.** Agents behind NAT, on a laptop, in a CI runner,
in a Lambda — all identical. That's why Temporal's model won, and it costs us nothing.

### Where the analogy must stop

Temporal replays your *code* to rebuild state, which is why it constrains everything you write
to be deterministic. **An LLM agent can never satisfy that.**

> Oryxa replays **history for context**, not **execution for state**.

State is snapshotted, not reconstructed by re-running. Replay serves audit, observation, and
late-joiner catch-up. We get Temporal's deployment story without its biggest tax.

## 2. The spine: one ordered, attributable, chained log

Concurrency is real — many agents and humans act at once. The whole concurrency design is one
decision:

> **Workers are concurrent. The log is the single serialization point.**

Ordering is established in one place without locking anything. Context and Ledger are both
folds over that order.

### 2.1 The event

Adding the Ledger costs almost nothing *at* the Ledger — it's a read model. It raises the bar
**here**, because a projection can only report what the event carried at write time.

```
Event {
  seq        monotonic, session-scoped     # the ordering truth
  id         uuid
  session    SessionRef
  ts         wall clock — ADVISORY ONLY    # never used for ordering
  actor      PrincipalRef                  # who
  kind       string                        # what
  target     RegionRef + key               # on what
  payload    json | commitment             # content, or its hash
  caused_by  [seq]                         # derivation
  usage      Usage?                        # tokens / cost / calls, when reported
  prev_hash  bytes                         # tamper-evident chain
  hash       bytes
}
```

Three fields deserve their reasoning:

**`ts` advisory, `seq` authoritative.** Wall clocks across distributed agents skew. Every
ordering decision reads `seq`; `ts` is for humans only.

**`payload: json | commitment`.** Following the VIL pattern — cryptographically linked records
storing *commitments rather than raw content*, tamper-evident without a blockchain. Any
post-hoc edit breaks the chain. It also means payloads can be evicted later while the chain
stays intact and verifiable, which partially answers the unbounded-growth problem in §9.

**`caused_by` — the one thing that cannot be backfilled.** See §2.2.

### 2.2 Causation comes free from views

`caused_by` is what separates a ledger from a log file. Attribution answers "who wrote this";
causation answers "what was this derived from" — and in a multi-agent chain that's the only
question that matters. It is also the one field that is **impossible to reconstruct after the
fact**. No amount of later work recovers it. It's right on day one or it's never right.

The good news: because Oryxa serves every read through a view (§4.3), **the server already
knows what each peer read.** So causation is derived automatically from the peer's read-set
since its last write — zero agent cooperation required.

- Coarse but **safe**: it over-approximates (the agent read ten facts, used three). A superset
  is the correct bias for audit.
- Refinable: an agent that wants precision may declare `caused_by` explicitly.

This is the second time the view decision pays for itself, after context-window size. Worth
noting that a design where reads are server-mediated gets provenance nearly for free, while one
where agents hold their own context can never have it.

Reads themselves do **not** become events — they're tracked per-peer in memory and attached to
the next write. Reads aren't durable facts; they're inputs to one.

### 2.3 Log invariant: never coalesce, never dedupe

The governed-memory study found a write-path dedup optimization silently defeating a
correctness mechanism downstream: **206 of 400 writes rejected pre-commit, dropping
contradiction detection from 100% to 49%.** The optimization was locally correct and globally
destructive.

Our exact analogue: any batching, coalescing, or dedup on the write path breaks the ledger.
State this as a hard invariant now, because it will look like an obvious performance win to
someone later. **Compaction is allowed on read models; the log itself is append-only, always.**

### 2.4 Event kinds (v1)

```
session.opened      session.closed
peer.joined         peer.left
context.appended    context.written
context.owned       context.released
conflict.rejected
usage.recorded
```

`conflict.rejected` is not bookkeeping — it's the diagnostic signal that two agents are
fighting over a region, which is exactly the design smell you want visible rather than buried
in client-side retry logic.

## 3. Sessions

```
Session:  open ──► closed
  members / presence / context regions / event log / SSE stream
```

| Kind | Reads | Writes | Notes |
|---|---|---|---|
| `agent` | yes | yes | framework-integrated worker |
| `human` | yes | yes | via UI or API; same events, different rendering |
| `observer` | yes | no | dashboards, evals, logging |

Humans and agents writing the same context is the product. It's safe because §4 makes conflicts
loud rather than silent.

**Presence** — who's here, who's active, what they last touched. Cheap, and it's the difference
between feeling multiplayer and feeling like a shared database.

## 4. Context

### 4.1 Two region types

Addressed as `/context/:region/:key`.

| Type | Semantics | Conflicts | For |
|---|---|---|---|
| `log` | append-only | **impossible by construction** | findings, observations, decisions, rationale |
| `state` | mutable, optimistic concurrency | surfaced as `409`, never silent | plans, status, structured working state |

`log` is the default and the recommended shape: it's what most agent output actually is, it's
conflict-free, and it makes provenance trivial. Every write it absorbs is a merge problem
nobody has to solve.

`doc` (CRDT) and `queue` (serializable) are deferred — the type field exists from day one, so
they're a new enum value later, not an API break.

### 4.2 OCC, because silent corruption is *the* failure mode

Every `state` read returns the seq it was observed at; every write must supply it. Stale write
→ `409` with the current value and the intervening events.

Deliberately the boring answer — HTTP ETags, basically — and the cheapest thing that addresses
the biggest documented failure mode. Lost updates, dirty reads, and cascade contamination that
**poisoned 87% of downstream decisions in four hours** are lethal precisely because the result
is *syntactically valid and semantically wrong*: it surfaces as a model failure, so teams blame
the LLM and never find the bug.

**OCC doesn't prevent conflicts; it makes them loud.** For v1 that beats a merge strategy
that's clever and occasionally wrong. Last-write-wins is explicitly rejected — it fails outright
under clock skew.

**Ownership** is the opt-in escalation: claim a region for exclusive write, turning 409s into
"someone else holds this." For regions where retrying is expensive.

### 4.3 Views — context by reference, not by copy

A peer declares which regions it needs and receives only those, as snapshot + RFC-6902 JSON
Patch deltas (the wire format AG-UI has already proven).

```
GET  /sessions/:id/context                → snapshot of your view
GET  /sessions/:id/context?since=:seq     → deltas
PUT  /sessions/:id/context/:region/:key   → write (If-Match: :seq)
POST /sessions/:id/context/:region        → append (log regions)
GET  /sessions/:id/stream                 → SSE: deltas + presence + events
```

Views earn their place three times over: smaller context windows, context-by-reference instead
of by-copy (the thesis), and automatic causation (§2.2).

## 5. Ledger

Two projections over the same log. **Neither is writable** — if a feature wants to write to the
Ledger, the answer is always an event.

### 5.1 Provenance — "who did that?"

Closes the attribution gap: audit logs normally record *the user or service that ran the
operation*, not *the agent that produced the upstream data it acted on*. Walking `caused_by`
backward gives the derivation chain for any value.

```
GET /sessions/:id/ledger/provenance/:region/:key   → derivation chain for a value
GET /sessions/:id/ledger/trace/:seq                → what caused this event, what it caused
GET /sessions/:id/ledger/verify                    → hash-chain integrity check
```

Feasible at interactive speed: the governed-memory study reconstructed 50/50 depth-four chains
with 100% writer-identity preservation at **p50 291ms per hop**. An audit UI over a derivation
graph is a real product, not an aspiration.

### 5.2 Resource — "who spent that?"

Tokens, cost, and tool calls attributed per principal per session.

```
GET /sessions/:id/ledger/usage                 → totals
GET /sessions/:id/ledger/usage?by=principal    → attributed
```

Nobody owns this today — A2A explicitly disclaims billing/ledger/cost tracking. It's also the
part of Oryxa a buyer *feels* on day one, whereas correctness guarantees stay invisible until
they fail. For a project whose other benefits are all preventative, that matters.

### 5.3 The tier ladder has a second axis now

Integration tier already determined context-sync fidelity. It also determines **ledger
completeness**, and this must be stated plainly rather than discovered:

| Tier | Context sync | Provenance | Resource |
|---|---|---|---|
| 0 — MCP | LLM-mediated, best-effort | complete for what flows through Oryxa | **blind to model calls** |
| 1 — attach | automatic | complete | complete where the framework exposes usage |
| 2 — client | explicit | complete | complete, caller-reported |

Tier 0 cannot see token usage — the model calls never touch us. An honest capability matrix in
the docs, not a footnote.

## 6. Integration — the "one URL" payoff

**Tier 0 — zero code.** One MCP server added to the agent's existing config; it gains
`read_context` / `append_context` / `write_context`. Works with any MCP-capable framework,
which in 2026 is effectively all of them.

```jsonc
{ "mcpServers": { "oryxa": { "url": "https://oryxa.internal/mcp?session=..." } } }
```

**Tier 1 — one line.** Native hooks sync automatically, no tool-calling in the loop.

```python
oryxa.attach(my_existing_agent, url="https://oryxa.internal", session="...")
```

**Tier 2 — client.** Explicit reads and writes when you want control.

## 7. Build order — one thing at a time

| # | Ship | Demo that proves it |
|---|---|---|
| 1 | **Event log** — full schema, seq, hash chain, read range | replay a session's history from scratch; `verify` passes |
| 2 | **Sessions** — create, join, leave, members, presence | two clients see each other join |
| 3 | **Context** — regions, `log` + `state`, OCC, views, read-set tracking | two agents write concurrently → clean 409, no lost data |
| 4 | **Stream** — SSE, snapshot + deltas, late-joiner catch-up | a third client joins mid-run and is instantly current |
| 5 | **Ledger** — provenance walk, usage rollup, verify | ask "why does this value say X" and get the chain back |
| 6 | **Tier 0 adapter (MCP)** | an unmodified off-the-shelf agent joins a live session |
| 7 | **Tier 1 adapter (attach)** | the same agent syncing automatically, no tool calls |

Step 1 now carries the Ledger's weight — get the event schema right and step 5 is a weekend of
read models. Get it wrong and step 5 is impossible.

**Step 3 proves the core claim.** Two real agents writing concurrently, conflict surfaced, no
data lost.
**Step 5 is the differentiator** — nobody else can answer "why does this value say X."
**Step 6 is what sells it** — an unmodified agent joining a shared session with one config line.

## 8. In / out for v1

**In:** sessions & membership · presence · `log` + `state` regions · OCC · optional exclusive
ownership · views · attributable hash-chained event log · automatic causation · snapshot +
deltas · SSE · REST · provenance ledger · resource ledger · chain verification · MCP endpoint ·
Tier 0/1/2.

**Free consequences of the log:** late-joiner catch-up · crash recovery via snapshot + tail ·
full audit trail · replay.

**Out:** tasks & routing · delegation grants · `doc` / `queue` regions · child sessions ·
Continuity beyond replay · federation · A2A egress/ingress · Governance beyond session-scoped
auth.

## 9. Open decisions

1. **Session vs Space** — still the only one where a wrong guess costs a migration, not a
   refactor. *Lean: Sessions only; key events so a Space fits above later.*
2. **Payload retention** — with commitments (§2.1), payloads can be evicted while the chain
   stays verifiable. What's the default policy? *Lean: keep everything in v1, ship the
   commitment field so eviction is possible without a format change.*
3. **Usage reporting shape** — who normalizes token/cost across providers, adapter or server?
   *Lean: adapter reports raw provider usage, server normalizes, so pricing tables live in
   one place.*
4. **Conflict ergonomics** — auto-retry on 409 in the client, or always the caller's call?
   *Lean: both exposed; default auto for `log`, manual for `state`.*
5. **Auth model** — session-scoped tokens is the obvious minimum; confirm it's enough for first
   users.
6. **Core language** — needed before code starts.
